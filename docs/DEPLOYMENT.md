# Deploying to Render

The API is deployed as a **Docker web service** with a **managed PostgreSQL** database, both
provisioned from [`render.yaml`](../render.yaml). The result is a public HTTPS URL serving the API
and its live Swagger UI.

> **Why PostgreSQL and not SQLite?** Free Render web services have an **ephemeral filesystem** —
> local files are lost on every redeploy, restart, or idle spin-down
> ([Render: Deploy for Free](https://render.com/docs/free)). A SQLite file would therefore be wiped
> regularly. Managed PostgreSQL is what makes the deployment durable.

## 1. Push the code

From the repository root:

```powershell
$env:PATH += ";C:\Program Files\Git\cmd"

git add -A
git commit -m "chore(deploy): Render blueprint, health probe, PostgreSQL migration set"
git push origin dev
```

> If you deploy from `main` instead, merge first: `git checkout main; git merge dev; git push origin main`.
> The repository is `https://github.com/JMNSJ/Web-Api-Cobsccomp251p-040`.

---

## 2. Create the stack from the blueprint

1. Sign in to the Render Dashboard.
2. Click **New → Blueprint**.
3. Connect the GitHub repository `Web-Api-Cobsccomp251p-040`.
4. Render detects `render.yaml` and shows the resources it will create:
   - `slsea-solar-db` — free PostgreSQL 16 (1 GB)
   - `slsea-solar-api` — free Docker web service
5. Confirm the **Blueprint name** and click **Apply**.

Render now provisions the database, builds the Docker image, and starts the service. The first
build takes roughly 3–6 minutes.

### What the blueprint sets for you

| Variable | Value | Why |
|----------|-------|-----|
| `ConnectionStrings__SolarDb` | injected from the database | The credential is never stored in git |
| `Database__Provider` | `Postgres` | Selects the Npgsql provider |
| `Database__MigrateOnStartup` | `true` | Applies the migration on boot |
| `Database__SeedOnStartup` | `true` | Seeds the dataset on first boot |
| `Jwt__SigningKey` | generated by Render | Secret, kept out of the repository |
| `Http__SkipHttpsRedirect` | `true` | Render's proxy already terminates TLS; an app-level redirect would loop |

## 3. Watch the first deploy

Open the **Logs** tab for `slsea-solar-api`. A successful first boot ends with:

```
info: DatabaseSeeder[0]
      Seeding provinces and districts...
info: DatabaseSeeder[0]
      Seed complete: 9 provinces, 25 districts, 29 substations, 210 installations, 141120 readings.
info: Microsoft.Hosting.Lifetime[14]
      Now listening on: http://0.0.0.0:10000
info: Microsoft.Hosting.Lifetime[0]
      Application started. Press Ctrl+C to shut down.
```

Seeding ~141k readings takes about 30–60 seconds on the free instance.

Render marks the deploy live once `GET /health` returns 200. That endpoint only answers 200 when the
database is reachable, so a service is never marked healthy with a broken data layer.

## 4. Get your URLs

The service page shows a URL like:

```
https://slsea-solar-api.onrender.com
```

| What | URL |
|------|-----|
| **Swagger UI** | `https://slsea-solar-api.onrender.com/` |
| **OpenAPI document** | `https://slsea-solar-api.onrender.com/swagger/v1/swagger.json` |
| **Health probe** | `https://slsea-solar-api.onrender.com/health` |

The Swagger UI is served at the **site root**, so the bare deployment URL lands directly on the
documentation. It is enabled in **every** environment, not just Development — that is what the brief
requires, and it is why `Program.cs` calls `UseSwagger()` unconditionally.

Verify from your machine:

```powershell
Invoke-RestMethod "https://slsea-solar-api.onrender.com/health"
# status        database  timestamp
# ------        --------  ---------
# healthy       reachable 4/10/2026 ...
```

## 5. Redeploying after code changes

`autoDeploy: true` is set, so **any push to the connected branch redeploys automatically**. To deploy
manually, use **Manual Deploy → Deploy latest commit**.

On a redeploy the database is untouched — the seeder checks for existing provinces and exits
immediately, so rows are never duplicated. The migration runs again but is a no-op once applied.

## Free-tier behaviour to expect

| Behaviour | Detail |
|-----------|--------|
| **Cold starts** | The service spins down after **15 minutes idle** and takes **~1 minute** to wake on the next request ([Render: Deploy for Free](https://render.com/docs/free)). Load the URL a minute before a demo. |
| **Instance hours** | 750 hours per workspace per month. Spun-down services do not consume hours. |
| **Database expiry** | Free PostgreSQL **expires 30 days after creation**, then a 14-day grace period before deletion. Re-create and re-seed if you need it longer. |
| **No persistent disk** | Not available on the free plan — this is exactly why PostgreSQL is used. |
| **Cold-start seeding** | Not repeated. Data lives in PostgreSQL, not the container. |

## Troubleshooting

**Deploy fails at `dotnet restore` or `dotnet publish`**
Check the build logs. The most common cause is the target framework — the Dockerfile uses the
`.NET 10` images (`mcr.microsoft.com/dotnet/sdk:10.0`). If you retarget the project to `net8.0`, you
must change both `FROM` lines to `8.0`.

**`No 'SolarDb' connection string was supplied for the Postgres provider`**
The `fromDatabase` wiring did not resolve. Confirm the database and service are in the same blueprint
and that the env var is named exactly `ConnectionStrings__SolarDb` (double underscore).

**Deploy is live but `/health` returns 503**
The service cannot reach PostgreSQL. Check the database is `Available` in the dashboard, and confirm
`Database__Provider` is `Postgres`.

**Swagger UI loads but shows no endpoints**
Expected until the API controllers are implemented (steps 5–13 of `PROJECT.md`). Only `/health`
exists so far.

**Service is slow on the first request after a while**
That is the free-tier cold start, not a fault. Warm it with a request before demonstrating.

## Alternative hosts

The same `Dockerfile` runs unchanged on any container host, because the app reads the injected
`PORT` and honours forwarded headers:

- **Fly.io** — supports persistent volumes, so SQLite would also work there
- **Azure App Service** — use the Web App for Containers plan; a free tier exists
- **Railway / Koyeb** — similar model to Render

Only Render needs the `render.yaml`; the others take the Dockerfile directly.
